# Kocotree Skills 发布手册

本文档说明 Kocotree Skills 的版本规则、更新说明写法、Tag 发布流程、CI/CD 行为、
Release 检查和自动更新验证方式。

## 1. 发布原则

- 发布由 `v*` Git Tag 触发，例如 `v0.1.11`。
- Tag 必须指向已经提交并推送的发布提交；未提交文件不会进入 CI 构建。
- Tag 版本必须与应用版本完全一致，否则 CI 会拒绝发布。
- 每个版本只发布一次，不覆盖已经正式发布的 Tag 和安装包。
- Release 默认生成 Draft，检查完成后必须人工点击 **Publish release**。
- **推送 Tag 会同时构建并部署生产后端，不只是发布桌面客户端。** 不要使用正式
  Tag 测试 CI 配置。

## 2. 版本规则

项目使用语义化版本 `主版本.次版本.修订版本`：

- 修复问题、优化体验或调整超时：增加修订版本，例如 `0.1.10` → `0.1.11`。
- 增加向后兼容的新功能：增加次版本，例如 `0.1.11` → `0.2.0`。
- 存在不兼容改动：增加主版本，例如 `0.2.0` → `1.0.0`。

发布前必须同步修改：

```text
package.json
src-tauri/tauri.conf.json
src-tauri/Cargo.toml
src-tauri/Cargo.lock 中 kocotree-skills-desktop 包的版本
```

Tag 使用相同版本并添加 `v` 前缀。例如应用版本为 `0.1.11` 时，Tag 必须为
`v0.1.11`。

## 3. 更新说明规则

更新说明统一写在仓库根目录的 `发布说明.md`。CI 会读取该文件，并将内容同时写入
GitHub Release 和自动更新使用的 `latest.json`。

编写规则：

- 使用中文，面向普通用户描述结果。
- 只填写具体条目，不要重复写“本次更新”标题，客户端页面已经包含该标题。
- 建议写 3～8 条，每条只描述一个变化。
- 优先使用“新增、优化、修复、提升”等动词开头。
- 不写文件名、函数名、提交哈希、密钥或仅开发人员能理解的内部实现。
- 尽量说明具体修复内容，避免长期只写“修复已知问题”。

示例：

```markdown
- 优化客户端自动更新体验
- 修复 macOS 无法识别更新包的问题
- 提升慢速网络下的下载和安装稳定性
```

必须在创建 Tag 前更新并提交 `发布说明.md`。Tag 创建后再修改该文件，不会改变该版本
已经生成的 `latest.json`。

## 4. 发布前检查

- [ ] 本次功能和修复已经完成。
- [ ] 四处应用版本已经统一。
- [ ] `发布说明.md` 已填写本次中文更新说明。
- [ ] `TAURI_SIGNING_PRIVATE_KEY` 已配置在 GitHub Actions Secrets。
- [ ] Tauri Updater 私钥已有安全备份，私钥没有进入仓库。
- [ ] 当前分支包含本次需要发布的全部改动。
- [ ] 已确认本次 Tag 可以同时部署生产后端。
- [ ] `git status --short` 没有遗漏的未提交文件。

当前工作流会在 CI 中自动执行前端测试、前端构建、后端类型检查和桌面端 Rust 测试。

## 5. 提交、推送和创建 Tag

下面以发布 `v0.1.11`、当前分支为 `nangua` 为例。实际操作时必须替换为目标版本。
本次功能代码应当已经提交；发布提交只包含版本号和更新说明等发布准备改动。

```bash
git status --short
git add package.json '发布说明.md' src-tauri/Cargo.toml src-tauri/Cargo.lock src-tauri/tauri.conf.json
git commit -m "chore: release v0.1.11"
```

先推送发布提交：

```bash
git push git@github.com:kocotree/kocotree-skills-desktop.git nangua
```

再创建带说明的 Tag 并推送：

```bash
git tag -a v0.1.11 -m "Kocotree Skills v0.1.11"
git push git@github.com:kocotree/kocotree-skills-desktop.git v0.1.11
```

如果 `origin` 已配置为具有正确权限的 SSH 远端，也可以使用 `git push origin`。
HTTPS Token 修改 `.github/workflows/` 时必须具有 `workflow` 权限，否则 GitHub 会拒绝
推送。

## 6. CI/CD 会执行什么

推送 Tag 后，`.github/workflows/release.yml` 按以下顺序运行：

1. 校验 Tag、`package.json`、`tauri.conf.json` 和 `Cargo.toml` 的版本一致。
2. 安装依赖，测试并构建前端。
3. 生成 Prisma Client，并检查后端构建。
4. 构建后端 Docker 镜像并推送到 GHCR。
5. 通过 SSH 将带 Tag 的后端镜像部署到生产服务器，并检查健康接口。
6. 并行构建 Windows x64、macOS Apple Silicon 和 macOS Intel 客户端。
7. 使用 Tauri Updater 私钥生成更新签名和 `latest.json`。
8. 创建 GitHub Draft Release 并上传安装包。

任一前置任务失败，后续任务不会继续。可以在 GitHub 仓库的 **Actions** 页面查看日志。

## 7. Draft Release 检查

CI 全部成功后，进入 GitHub 仓库的 **Releases** 页面，打开对应 Draft。

确认 Tag、标题、中文更新说明正确，并至少包含：

```text
macOS Apple Silicon:
  *_aarch64.app.tar.gz
  *_aarch64.app.tar.gz.sig
  *_aarch64.dmg

macOS Intel:
  *_x64.app.tar.gz
  *_x64.app.tar.gz.sig
  *_x64.dmg

Windows x64:
  *_x64-setup.exe
  *_x64-setup.exe.sig
  *_x64_en-US.msi
  *_x64_en-US.msi.sig

自动更新清单:
  latest.json
```

查看 `latest.json`，确认至少存在：

```text
darwin-aarch64
darwin-x86_64
windows-x86_64
```

每个平台条目都必须同时具有有效的 `url` 和 `signature`。

确认无误后，保持 Release label 为 `None`，不要选择 Pre-release，然后点击绿色的
**Publish release**。

Draft 不会被 `/releases/latest/` 识别。未点击 Publish 时，客户端检查更新可能收到
404 并显示“暂时无法检查更新”。

## 8. 发布后验证

发布后等待几十秒，检查公开更新清单：

```bash
curl --fail --location --silent \
  https://github.com/kocotree/kocotree-skills-desktop/releases/latest/download/latest.json
```

然后使用低于新版本的已安装客户端验证：

1. 打开“设置与关于”。
2. 点击“检查更新”。
3. 确认可用版本和中文更新说明正确。
4. 点击“立即更新”。
5. 确认下载、签名验证、安装和重启全部完成。
6. 重启后确认客户端版本已经更新。

客户端的下载和安装总超时当前为 1 小时。GitHub Release 在部分网络下可能较慢；如果
后续迁移到国内 OSS/CDN，应再次验证 `latest.json` 和所有平台下载地址。

## 9. 常见问题

### 客户端检查更新返回“暂时无法检查更新”

优先检查 Release 是否仍为 Draft、`latest.json` 是否能公开访问，以及它是否包含当前
操作系统和架构的平台键、下载地址和签名。

### macOS 可以下载 DMG，但自动更新失败

DMG 只用于手动安装。macOS 自动更新必须存在 `.app.tar.gz` 和对应 `.sig`。工作流中的
macOS 构建参数必须保留 `--bundles app,dmg`。

### CI 提示版本不一致

检查 Tag 与三个版本源文件是否一致，并确认 Tag 指向包含版本修改的提交。

### CI 提示缺少签名密钥

在 GitHub 仓库的 **Settings → Secrets and variables → Actions** 中确认存在
`TAURI_SIGNING_PRIVATE_KEY`。不要在日志、聊天或仓库中粘贴私钥。

### 下载速度很慢

GitHub Release 最终使用海外对象存储，部分网络可能很慢。短期可更换网络或使用代理；
长期方案是将签名后的更新包和 `latest.json` 同步到国内 OSS/CDN。

## 10. 失败版本处理

- CI 失败时不要发布不完整的 Draft Release。
- 已正式发布的版本不要直接覆盖安装包或复用 Tag。
- 修复问题后增加修订版本，重新提交并创建新 Tag，例如 `v0.1.11` → `v0.1.12`。
- 如果错误版本已经发布，应尽快发布更高的修复版本，并在更新说明中写明修复内容。
- 删除远端 Tag 或 Release 属于破坏性操作，只在明确评估影响后执行。

## 11. 签名说明

Tauri Updater 签名与操作系统代码签名是两套机制：

- Updater 私钥只保存在 GitHub Actions Secret 中，用于签署自动更新包。
- Updater 公钥写在客户端配置中，随客户端编译发布，用户不需要配置。
- Windows 当前没有系统代码签名，仍可能出现 SmartScreen 提示。
- macOS 当前使用 Ad-hoc 签名，仍可能需要用户在系统设置中允许打开。

私钥丢失后，已安装客户端将无法验证使用新密钥签署的后续更新，因此必须安全备份。
